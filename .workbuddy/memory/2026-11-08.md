## 翻书（Godot 移植版）翻页卡顿优化

**问题**：Unity 移植过来的 EndlessBook 翻书，连续翻页实测只有 13 fps，每帧 50~140 ms。

**根因（四处叠加）**：
1. `assets/video/粒子背景.ogv` 是 **3840x2160 @25fps 的 Theora**。Godot 的 Theora 是 CPU 软解，
   单帧解码 50~140 ms —— 这是绝对主因（占 95% 开销）。而且它只被渲染进 1280x720 的 SubViewport，
   等于 4K 解完立刻缩成 720p。
2. `assets/pages*` 的 PNG 用「无损」导入（`.ctex` 里其实是 PNG 数据），每张首次使用要在主线程
   解码 17~31 ms，渲染线程再卡 40~70 ms。
3. `ImageLoaderManager` 照搬 Unity 启动全量加载 86 张页面 → 启动 6.1 s、占 1.4 GB 显存，
   而 `loaded_materials` 没有任何调用方。
4. `PageCache` 用 `CACHE_MODE_IGNORE` + 容量 12，淘汰不区分是否正在显示。

**改动**：
- 视频从 mp4 重转 1280x720 Theora（ffmpeg libtheora q8，lanczos），仍叫 `粒子背景.ogv`。
- 172 个 `*.png.import` 改为 `compress/mode=2` + `compress/high_quality=true`（BC7/BPTC）。
  实测 PSNR 47.8 dB、平均误差 0.44，肉眼无损；单张显存 15.8 MB → 4.1 MB。
  重新导入：`godot --headless --path . --import`（约 4.5 分钟，`.godot/imported` 390 MB → 707 MB）。
- `image_loader_manager.gd` 加 `preload_all_pages`（默认 false）。
- 重写 `page_cache.gd`：LRU(16) + 每帧最多预载 1 页 + 当前左右页不淘汰；同步加载（BC7 下 2~4 ms，不必异步）。
- `fanshu.gd` / `fanshu2.gd`：预载半径 back3/forward8，启动预热 6 页；修 max_img 判定。
- `endless_book.gd`：无实质改动（曾加 refresh_spread，最后随异步方案一起去掉）。

**结果**：连续翻页 720~800 fps（p50/p95 2 ms、p99 4 ms、最大 16~34 ms，>33ms 帧 0~1 个）；
启动 6130 ms → 356~580 ms；显存 2308 MB → 173~232 MB。

**工具/环境**：
- Godot 实际路径：`D:\Program Files\Godot Engine\Godot_v4.7.2-stable_win64.exe\Godot_v4.7.2-stable_win64_console.exe`
  （注意目录名本身带 `.exe`，真正的 exe 在它里面）。
- 本机无 ffmpeg，从 `cdn.npmmirror.com/binaries/ffmpeg-static/b6.1.1/ffmpeg-win32-x64.gz` 下的，
  放在 `C:\Users\Vino\AppData\Local\Temp\ffm\ffmpeg`（含 libtheora 编码器）。
- pip 走清华镜像对本机不可用（返回 none），网络本身通。
- `_perf_diag.gd` 已扩展 `--video=` / `--vres=` / `--interval=` 参数，`_shots.gd` 出截图，`_audit.gd` 校验目录跳转。
- headless 无法渲染视口截图，要用带窗口模式。

**已验证**：两场景正常启动无报错；目录按钮 40+ 项跳转页码与图片全部 OK；页面文字清晰无 BC7 块状伪影。

## 修：背景视频变成一条横带（不平铺）

**现象**：背景视频只占屏幕中间一条横带（约窗口高度的 1/5），上下露出 Environment 背景色。

**根因**：`background_video.gd` 里用
`xf.basis = xf.basis.scaled(Vector3(w, h, 1.0))` 给面片设尺寸。
**Godot 的 `Basis.scaled()` 是按行（rows）缩放**，不是按基向量列缩放。
相机基是带旋转的（`Y=(0,0,-1)`、`Z=(0,1,0)`），于是：
- 宽度那一下（乘 w）落在 row0 → 世界 X 轴，正好对；
- 高度那一下（乘 h）落在 row1 → 世界 -Y 方向的列分量，结果缩放跑到了 `Z` 轴（相机前后方向，平面法线），
  `basis.y` 仍是单位长度。

实测面片变换：`X=(8.29,0,0) Y=(0,0,-1) Z=(0,4.66,0)`，
即宽 8.29、高只有 1，而 5 米处可见高度是 4.66 → 只覆盖 21% 屏高。

**修法**：显式按列构造
`Transform3D(Basis(b.x * w, b.y * h, b.z), origin)`，
并顺手把宽高比从「设计分辨率」改成「真实视口像素尺寸」（`get_viewport().size`），
非 16:9 窗口下也正确；正交相机走 `cam.size`。

**教训**：Godot 4 里 `Basis.scaled()` = 缩行，等价于 `diag(s) * M`（缩放世界轴）；
想沿物体自身轴缩放要用列缩放的写法（`Basis(col0*sx, col1*sy, col2*sz)`）。
